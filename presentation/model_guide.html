STEP 0What is this Kaggle competition?

Kaggle is a website where companies and universities post data-science challenges. You download a training dataset, build a model that solves the problem, and submit your predictions on a test set whose answers are hidden. Kaggle scores them automatically and ranks the teams.

In our case, the "company" is the ESADE Data Science for Finance course (term 3, 2026). The challenge is called Personal Loan Credit Decision.

The business question

A bank receives loan applications. For each one, a human credit analyst has to decide: approve or reject. The bank gives us 25,000 historical applications with the decision the analyst actually made, and asks us to build a model that can make the same kind of decision automatically for 5,000 new applications.

TopicDetail
Type of problemBinary classification (output is 0 or 1)
Target columncredit_decision — 1 = approved, 0 = rejected
Train data25,000 rows, target included
Test data5,000 rows, target hidden
Evaluation metricAccuracy — % of rows the model gets right
Submission formatCSV with 5,000 rows: id, credit_decision
Public / Private split40% public (2,000 rows visible during the competition), 60% private (3,000 rows — graded at the end)
Submission limit5 per day, 2 finals count for the leaderboard
Think of it like an exam where 40% of the answers are graded immediately and shown to you (the public score), and the other 60% are graded at the end and decide your final mark (the private score). You don't want to "memorise" the 40% — you want to actually learn the material, because the 60% is the one that counts.

The standard data-science workflow looks like this:

The standard ML workflow — same every time, but the hard part is doing each step right.

For this competition we added an extra phase at the start: forensics. The professor said the dataset has unreliable columns, so before doing anything else we audited every column for trustworthiness. Three columns failed the audit (the "three traps", see Step 4).

STEP 3Exploratory analysis — what we saw

Three things jumped out immediately.

1. The target is nearly balanced

52% approved, 48% rejected. Always guessing "approved" would only get you 52% — every percentage point above that has to be earned by the model.

2. Massive missing values

Some columns are 90–97% missing (especially the credit scores). external_pd_score looks 95% present in train, but in test it's 100% missing. A red flag.

3. The data is messy

  • date appears in two formats: 2022-06-08 and Apr-2026, roughly 50/50.
  • prev_default uses {Yes, 1, '1'} for "yes" and {No, 0, '0'} for "no" — inconsistent encodings.
  • ann_income values range from 10 to millions — the log-histogram is bimodal: half the rows are in units of currency, the other half in thousands.
Example of the bimodal income. One row says ann_income = 65 (means $65,000), the next says ann_income = 72400 (means $72,400). Without fixing this, the model would think the first applicant earns 1000× less than they really do.

STEP 4The three traps the professor planted

The most important step. We treated the brief as adversarial input. Three columns failed the audit.

Trap 1 — internal_code: a planted leak

Looks like the best feature in the dataset:

  • Correlation with the target in train: +0.92
  • A trivial rule "approve if internal_code > 50" hits 99.1% accuracy on the training set

It looks like a gift. But anything that simple in a dataset that was "assembled from multiple legacy source systems" is a hypothesis to test, not a result.

How we caught it — the opinion-probe

The column analyst_opinion contains 60 fixed template sentences, and the same 60 templates appear in both train and test. So the average approval rate per template (computed on train) is a stable proxy for the underlying "risk signal" we are trying to predict. Any genuine feature must relate to that proxy the same way in train and in test. Let's check:

opmap = train.groupby('analyst_opinion').credit_decision.mean()
tr_op = train.analyst_opinion.map(opmap)
te_op = test.analyst_opinion.map(opmap)

train.internal_code.corr(tr_op)   # +0.46  → looks like real signal
test.internal_code.corr(te_op)    # ≈ 0.00 → but it's noise in test

Same average and spread of values in train and test, but in test the values are decoupled from every other risk feature. The values were scrambled in the test set. DROP

Without this catch, the model would score ~99% in cross-validation and ~52% on the hidden private 60%. A disaster, masked.

Trap 2 — external_pd_score: vanishes in test

5% missing in train (perfectly usable). 100% missing in test (completely unusable).

A model that relies on this column has nothing to predict with at inference time.

Caught in one line of code:

train.isna().mean()   # external_pd_score → 5%
test.isna().mean()    # external_pd_score → 100%

DROP

Trap 3 — race, religion: the ethical trap

These two columns are included in the data as synthetic codes. The brief flags them: "may be subject to legal and regulatory limitations for fairness and discrimination-related issues."

We measured what happens if you use them: +0.7 pt accuracy (0.859 → 0.866).

We refused. Four reasons:

  • Legal — using protected attributes in credit decisions is illegal in both the EU (GDPR) and the US (ECOA).
  • Ethical — historical analyst bias is encoded in the target. Reproducing it would amplify it.
  • Practical — a model that depends on protected attributes can't be deployed.
  • Methodological — the brief flagged these columns. Using them would fail the implicit ethics question.

DROP

STEP 5Cleaning the messy data, step by step

Now the dataset is "clean enough to model" only after we systematically fix each format issue. All fixes live in one shared module (src/prep.py), so train and test are cleaned identically — no leakage.

Fix 1 — Dates in two formats

def parse_dates(s):
    iso = pd.to_datetime(s, format='%Y-%m-%d', errors='coerce')   # 2022-06-08
    mon = pd.to_datetime(s, format='%b-%Y',    errors='coerce') + pd.Timedelta(days=14)  # Apr-2026
    return iso.fillna(mon)

We try the ISO format first; if it fails we try the Mon-YYYY format and date it mid-month. After this, every row has a usable date.

Fix 2 — Income unit mismatch

inc = pd.to_numeric(df['ann_income'], errors='coerce')
out['ann_income'] = np.where(inc < 700, inc * 1000, inc)

The log-histogram of ann_income has an empty gap between 700 and 2000 — there are no observations there because no one earns exactly $1,000 a year. That gap is the signature of two populations mixed together: rows in thousands vs rows in units. We multiply by 1,000 below the gap.

Fix 3 — Unified prev_default

out['prev_default'] = df['prev_default'].map({'0':0,'No':0,'1':1,'Yes':1}).astype(float)

Just normalising different ways of saying yes / no.

Fix 4 — Recover missing age from birth year

out['age'] = df['age'].fillna(out['year'] - df['birth_year'])

About 10% of rows are missing age but have birth_year. Decision year minus birth year = age. We checked this is consistent on the rows where both are present (median mismatch = 0).

Fix 5 — Risk indicators 1 and 2 are the same variable

out['risk12'] = df['risk_indicator_1'].fillna(df['risk_indicator_2'])

On the rows where both are present, their correlation is exactly 1.0. So they are literally the same variable from two source systems. We coalesce them into one column risk12 and keep risk3 separate.

Fix 6 — Credit scores on three different scales

for c in ['cr_scores_fico','cr_scores_vantage','cr_scores_schufa']:
    mu, sd = train[c].mean(), train[c].std()        # train only — no test peeking!
    train[c+'_z'] = (train[c] - mu) / sd
    test[c+'_z']  = (test[c]  - mu) / sd
credit_z = fico_z.fillna(vantage_z).fillna(schufa_z)

FICO, Vantage and SCHUFA all use different scales. We standardise each one against its own mean / standard deviation (computed only on train), then coalesce into one column called credit_z.

Why "train only"?

If you compute the standardisation using train and test together, you are using information from the test set during training. This is called data leakage. It rarely changes the result much with tree models, but it's a methodological error. We corrected it in prep_v2.py.

STEP 6Feature engineering — building new signals

"Feature engineering" means creating new columns from the existing ones to expose patterns the model would otherwise miss.

The risk indicators have an inverted-U pattern

Linear correlation between risk_indicator_3 and the target is only −0.08, which looks worthless. But when you plot approval rate by risk decile, the relationship is not linear at all:

  • Risk around 50 (the middle): ~65% approval
  • Risk above 78: ~26% approval
  • Risk below 20: also lower approval

The signal is distance from the middle, not the raw value. We encode that:

X['risk12_dev'] = (X.risk12 - 55).abs()    # distance from "safe" middle
X['risk3_dev']  = (X.risk3  - 55).abs()
X['risk_max']   = X[['risk12','risk3']].max(axis=1)
X['risk_mean']  = X[['risk12','risk3']].mean(axis=1)

These engineered features end up in the top of the importance ranking — the raw indicators alone would have been almost useless.

The opinion column — a happy surprise

analyst_opinion only has 60 unique values across the entire dataset — they are fixed template sentences. We don't need natural-language processing (TF-IDF, embeddings…). We just treat it as a categorical column with 60 levels. The model learns the approval rate of each template directly.

This is why analyst_opinion ends up as the strongest single feature in the model.

STEP 8Choosing a model: simple → complex

We didn't start from a complicated model. We compared families with the same 5-fold cross-validation, accuracy as metric:

Model5-fold accuracyWhat it is
Naive Bayes0.7597The simplest probabilistic baseline
LDA0.7770Linear discriminant analysis
Logistic Regression0.7835Classic linear classifier
Random Forest0.8334An average of many decision trees
Single LightGBM0.8358Gradient-boosted trees (state-of-the-art for tabular data)
Ensemble (LGBM+XGB+CAT)0.8590Multiple boosted-tree models, averaged
The progression looks like climbing a ladder. Each step adds about +0.5–1.5 pt of accuracy. Gradient boosting clearly dominates on tabular data with mixed numeric/categorical columns and missing values — exactly what we have.

STEP 9The ensemble — why 16 models, not 1

Different model families make different mistakes. If we average their predictions, the random part of each model's error cancels out, and the genuine signal remains. That's why ensembling usually beats any single model.

Our 16 members

  • 9 × LightGBM — 3 hyperparameter configurations (found via random search), each trained with 3 different random seeds.
  • 3 × XGBoost — 3 random seeds.
  • 4 × CatBoost — 2 configurations × 2 seeds. Especially good at handling the 60-template analyst_opinion column.

Each member is trained with 5-fold cross-validation. Final ensemble = simple average of the 16 probability vectors.

From features to a single final probability per row.

Pseudo-labeling: a semi-supervised trick

After training the ensemble once, look at its test-set predictions. For test rows where the ensemble is ≥ 97% confident, we trust the prediction and use it as a "fake label" — adding those rows to the training data at half weight, and retraining. This squeezes a small extra signal from the test set without leaking.

STEP 10Validation — how we know it really works

Picking the right way to measure performance is as important as picking the right model.

Three independent validation lenses

SchemeWhat it catches
5-fold Stratified K-FoldGeneral performance, used to tune the threshold
Time split (train ≤ 2024 → predict 2025–26)Temporal drift a random split would hide
Rolling next-month harnessClosest simulation of the real task

What is a rolling next-month harness?

For each of the last 6 months in the training data:

  1. Pretend that month is "the test set"
  2. Train the model on everything that came before
  3. Predict the held-out month

This gives 2,886 out-of-time predictions. Crucially, it mimics the real task: train ends April 2026, real test is May 2026 → train on the past, predict the next month. Every experiment was judged here, not on the public leaderboard.

Why this matters

A 5-fold random CV mixes 2022 rows with 2026 rows in both training and validation. That's not the real task. The real task is: given everything up to today, predict next month. The rolling harness is the only metric that simulates this honestly.

Adversarial validation

Quick safety check: can a classifier distinguish train rows from test rows? Trained one. AUC = 0.497 once date features are removed — meaning apart from time, train and test are identically distributed. So beyond the temporal shift we already handle, there are no hidden corruptions.

STEP 11The threshold — a hidden hyperparameter

A classifier outputs a probability, not a hard 0/1. To get a 0/1 label, we compare the probability with a threshold. Default is 0.5, but the optimum can be different — especially when accuracy is the metric.

oof = np.zeros(len(X))
for tr_i, va_i in StratifiedKFold(5, shuffle=True, random_state=42).split(X, y):
    m = lgb.LGBMClassifier(**params)
    m.fit(X.iloc[tr_i], y.iloc[tr_i],
          eval_set=[(X.iloc[va_i], y.iloc[va_i])],
          callbacks=[lgb.early_stopping(150)])
    oof[va_i] = m.predict_proba(X.iloc[va_i])[:, 1]

# Smoothed threshold — average of the top-1% candidates, NOT just the argmax
ths = np.linspace(0.35, 0.65, 601)
accs = [((oof > t) == y).mean() for t in ths]
smooth_t = ths[np.argsort(accs)[-6:]].mean()   # ≈ 0.527

Why "smoothed"?

If we just pick the single threshold that maximises OOF accuracy, we may pick a noisy peak that won't generalise. Averaging the top-1% of candidate thresholds gives a more robust value that holds up on unseen data.

STEP 14Lessons learned

  • Read the data dictionary as adversarial input. Every line is a clue.
  • One suspiciously strong feature is a leak hypothesis, not a result. Test it.
  • Always check train.isna() vs test.isna() — external_pd_score was caught in one line.
  • Validate against the real task, not against random folds. Rolling next-month was the metric that mattered.
  • Don't chase the public leaderboard. The noise floor is bigger than your improvements.
  • Sometimes the best feature engineering is deletion. We removed the 4 most "predictive" columns on purpose.
  • Quantify ethical choices. "We dropped race/religion" is weak. "Dropping them costs exactly +0.7 pt of bias-driven accuracy" is strong.

STEP 0Cos'è questa competizione Kaggle?

Kaggle è una piattaforma dove aziende e università pubblicano challenge di data science. Scarichi un dataset di training, costruisci un modello che risolve il problema, e submetti le tue predizioni su un test set di cui non vedi le risposte. Kaggle calcola lo score automaticamente e classifica i team.

Nel nostro caso, la "azienda" è il corso ESADE Data Science for Finance (term 3, 2026). La challenge si chiama Personal Loan Credit Decision.

La domanda di business

Una banca riceve domande di prestito. Per ognuna, un analista del credito deve decidere: approvare o rifiutare. La banca ci dà 25.000 domande storiche con la decisione che l'analista ha effettivamente preso, e ci chiede di costruire un modello che faccia lo stesso tipo di decisione in automatico per 5.000 nuove domande.

Non vuoi "memorizzare" il 40% — vuoi imparare davvero la materia, perché il 60% è quello che fa media.

STEP 3Analisi esplorativa — cosa abbiamo visto

Tre cose sono saltate fuori subito.

1. Il target è quasi bilanciato

52% approvati, 48% rifiutati. Indovinare sempre "approvato" arriverebbe a 52%. Ogni punto percentuale sopra quello va guadagnato col modello.

2. Tantissimi valori mancanti

Alcune colonne sono al 90–97% mancanti (specialmente i credit score). external_pd_score sembra presente al 95% nel train, ma nel test è 100% mancante. Un bel campanello d'allarme.

3. I dati sono disordinati

  • date appare in due formati: 2022-06-08 e Apr-2026, circa 50/50.
  • prev_default usa {Yes, 1, '1'} per "sì" e {No, 0, '0'} per "no" — codifiche inconsistenti.
  • ann_income va da 10 a milioni — il log-istogramma è bimodale: metà righe in unità, metà in migliaia.
Esempio del reddito bimodale. Una riga dice ann_income = 65 (significa $65.000), la successiva dice ann_income = 72400 (significa $72.400). Senza fixarlo, il modello penserebbe che il primo richiedente guadagni 1.000× meno di quanto in realtà guadagna.

STEP 4Le tre trappole del prof

Lo step più importante. Abbiamo trattato il brief come input avversariale. Tre colonne non hanno superato l'audit.

Trappola 1 — internal_code: leak piantato

Sembra la migliore feature del dataset:

  • Correlazione col target nel train: +0,92
  • Una regola banale "approva se internal_code > 50" arriva al 99,1% di accuracy sul training

Sembra un regalo. Ma qualcosa di così semplice in un dataset "assemblato da più sistemi legacy" è un'ipotesi da testare, non un risultato.

Come l'abbiamo beccato — l'opinion-probe

La colonna analyst_opinion contiene 60 frasi template fisse, e gli stessi 60 template appaiono sia in train che in test. Quindi il tasso medio di approvazione per template (calcolato sul train) è un proxy stabile del "segnale di rischio" che vogliamo prevedere. Una feature genuina deve correlare con quel proxy allo stesso modo in train e in test. Verifichiamo:

opmap = train.groupby('analyst_opinion').credit_decision.mean()
tr_op = train.analyst_opinion.map(opmap)
te_op = test.analyst_opinion.map(opmap)

train.internal_code.corr(tr_op)   # +0.46  → sembra segnale reale
test.internal_code.corr(te_op)    # ≈ 0.00 → ma nel test è rumore

Stessa media e dispersione dei valori in train e test, ma nel test i valori sono scollegati da ogni altra feature di rischio. I valori sono stati scrambleati nel test. DROP

Senza questa scoperta, il modello avrebbe fatto ~99% in cross-validation e ~52% sul 60% privato nascosto. Un disastro, mascherato.

Trappola 2 — external_pd_score: sparisce nel test

5% mancante nel train (utilizzabile). 100% mancante nel test (completamente inutile).

Un modello che dipende da questa colonna non ha nulla per fare predizioni a inference time.

Beccata con una riga:

train.isna().mean()   # external_pd_score → 5%
test.isna().mean()    # external_pd_score → 100%

DROP

Trappola 3 — race, religion: la trappola etica

Queste due colonne sono nel dataset come codici sintetici. Il brief le segnala: "possono essere soggette a limitazioni legali e regolamentari per fairness e questioni di discriminazione."

Abbiamo misurato cosa succede usandole: +0,7 pt accuracy (0,859 → 0,866).

Abbiamo rifiutato. Quattro motivi:

  • Legale — l'uso di attributi protetti nel credito è illegale sia in UE (GDPR) che negli USA (ECOA).
  • Etico — il bias storico degli analisti è codificato nel target. Riprodurlo lo amplifica.
  • Pratico — un modello che dipende da attributi protetti non può andare in produzione.
  • Metodologico — il brief segnalava queste colonne. Usarle significherebbe fallire la domanda etica implicita.

STEP 5Pulizia dei dati, passo passo

Ora il dataset è "abbastanza pulito da modellare" solo dopo aver sistemato ogni problema di formato. Tutti i fix vivono in un solo modulo condiviso (src/prep.py), così train e test vengono puliti in modo identico — niente leakage.

Fix 1 — Date in due formati

def parse_dates(s):
    iso = pd.to_datetime(s, format='%Y-%m-%d', errors='coerce')   # 2022-06-08
    mon = pd.to_datetime(s, format='%b-%Y',    errors='coerce') + pd.Timedelta(days=14)  # Apr-2026
    return iso.fillna(mon)

Proviamo prima il formato ISO; se fallisce proviamo Mon-YYYY e dattiamo a metà mese. Dopo questo, ogni riga ha una data utilizzabile.

Fix 2 — Reddito con unità di misura diverse

inc = pd.to_numeric(df['ann_income'], errors='coerce')
out['ann_income'] = np.where(inc < 700, inc * 1000, inc)

Il log-istogramma di ann_income ha un gap vuoto tra 700 e 2000 — non ci sono osservazioni lì perché nessuno guadagna esattamente $1.000 all'anno. Quel gap è la firma di due popolazioni mescolate: righe in migliaia vs righe in unità. Moltiplichiamo per 1.000 sotto il gap.

Fix 3 — prev_default unificato

out['prev_default'] = df['prev_default'].map({'0':0,'No':0,'1':1,'Yes':1}).astype(float)

Normalizziamo i diversi modi di dire sì / no.

Fix 4 — Recuperare età mancante dall'anno di nascita

out['age'] = df['age'].fillna(out['year'] - df['birth_year'])

Circa il 10% delle righe ha age mancante ma ha birth_year. Anno della decisione meno anno di nascita = età. Verificato che è consistente sulle righe in cui ci sono entrambi (mismatch mediano = 0).

Fix 5 — Risk indicator 1 e 2 sono la stessa variabile

out['risk12'] = df['risk_indicator_1'].fillna(df['risk_indicator_2'])

Sulle righe in cui entrambi sono presenti, la correlazione è esattamente 1.0. Sono letteralmente la stessa variabile da due sistemi sorgente. Le coalesciamo in una colonna sola risk12 e teniamo risk3 separata.

Fix 6 — Credit score su tre scale diverse

for c in ['cr_scores_fico','cr_scores_vantage','cr_scores_schufa']:
    mu, sd = train[c].mean(), train[c].std()        # solo train — niente sbirciatine al test!
    train[c+'_z'] = (train[c] - mu) / sd
    test[c+'_z']  = (test[c]  - mu) / sd
credit_z = fico_z.fillna(vantage_z).fillna(schufa_z)

FICO, Vantage e SCHUFA usano scale diverse. Standardizziamo ognuno rispetto alla propria media / deviazione standard (calcolate solo sul train), poi coalesciamo in una colonna chiamata credit_z.

Perché "solo train"?

Se calcoli la standardizzazione usando train e test insieme, stai usando informazione del test set durante il training. Si chiama data leakage. Raramente cambia molto il risultato con modelli a tree, ma è un errore metodologico. Lo abbiamo corretto in prep_v2.py.

STEP 6Feature engineering — costruire nuovi segnali

"Feature engineering" significa creare nuove colonne dalle esistenti per esporre pattern che il modello altrimenti mancherebbe.

I risk indicator hanno una forma a U rovesciata

La correlazione lineare tra risk_indicator_3 e il target è solo −0,08, che sembra inutile. Ma se plotti il tasso di approvazione per decile di rischio, la relazione non è affatto lineare:

  • Rischio attorno a 50 (centro): ~65% di approvazione
  • Rischio sopra 78: ~26% di approvazione
  • Rischio sotto 20: anch'esso approvazione più bassa

Il segnale è la distanza dal centro, non il valore grezzo. Lo codifichiamo:

X['risk12_dev'] = (X.risk12 - 55).abs()    # distanza dal centro "sicuro"
X['risk3_dev']  = (X.risk3  - 55).abs()
X['risk_max']   = X[['risk12','risk3']].max(axis=1)
X['risk_mean']  = X[['risk12','risk3']].mean(axis=1)

Queste feature finiscono ai primi posti della importance — i risk indicator grezzi da soli sarebbero stati quasi inutili.

STEP 9L'ensemble — perché 16 modelli, non 1

Famiglie di modelli diverse fanno errori diversi. Se mediamo le loro predizioni, la parte random dell'errore di ogni modello si cancella, e rimane il segnale vero. Per questo l'ensembling di solito batte qualsiasi singolo modello.

I nostri 16 modelli

  • 9 × LightGBM — 3 configurazioni di iperparametri (trovate via random search), ognuna allenata con 3 random seed diversi.
  • 3 × XGBoost — 3 random seed.
  • 4 × CatBoost — 2 configurazioni × 2 seed. Particolarmente bravo a gestire la colonna analyst_opinion da 60 template.

Ogni modello è allenato con 5-fold cross-validation. Ensemble finale = media semplice dei 16 vettori di probabilità.

Pseudo-labeling: un trucco semi-supervisionato

Dopo aver allenato l'ensemble una volta, guardiamo le sue predizioni sul test set. Per le righe del test in cui l'ensemble ha confidence ≥ 97%, ci fidiamo della predizione e la usiamo come "label finta" — aggiungendo quelle righe ai training data a peso 0,5, e riallenando. Spreme un piccolo segnale extra dal test set senza causare leak.

STEP 10Validazione — come sappiamo che funziona davvero

Scegliere il modo giusto di misurare la performance è importante quanto scegliere il modello giusto.

Tre lenti di validazione indipendenti

SchemaCosa cattura
5-fold Stratified K-FoldPerformance generale, usato per tunare la soglia
Time split (train ≤ 2024 → predire 2025–26)Drift temporale che un random split nasconderebbe
Rolling next-month harnessSimulazione più fedele del task reale

Cos'è una rolling next-month harness?

Per ognuno degli ultimi 6 mesi del training:

  1. Fai finta che quel mese sia "il test set"
  2. Allena il modello su tutto quello che è venuto prima
  3. Predici quel mese held-out

Questo dà 2.886 predizioni out-of-time. Cosa fondamentale, simula il task reale: il train finisce ad aprile 2026, il test reale è maggio 2026 → allena sul passato, predici il mese successivo. Ogni esperimento è stato giudicato qui, non sul public leaderboard.

Perché conta

Una random 5-fold CV mescola righe del 2022 con righe del 2026 sia in training che in validation. Non è il task reale. Il task reale è: dato tutto fino a oggi, predici il mese prossimo. La rolling harness è l'unica metrica che lo simula onestamente.

Adversarial validation

Check di sicurezza rapido: un classificatore può distinguere righe train da righe test? Ne abbiamo allenato uno. AUC = 0,497 una volta rimosse le feature di data — significa che a parte il tempo, train e test sono distribuiti in modo identico. Quindi oltre allo shift temporale che già gestiamo, non ci sono corruzioni nascoste.

STEP 11La soglia — un iperparametro nascosto

Un classificatore produce una probabilità, non un 0/1 secco. Per ottenere una label 0/1, confrontiamo la probabilità con una soglia. Il default è 0,5, ma l'ottimo può essere diverso — soprattutto quando la metrica è accuracy.

oof = np.zeros(len(X))
for tr_i, va_i in StratifiedKFold(5, shuffle=True, random_state=42).split(X, y):
    m = lgb.LGBMClassifier(**params)
    m.fit(X.iloc[tr_i], y.iloc[tr_i],
          eval_set=[(X.iloc[va_i], y.iloc[va_i])],
          callbacks=[lgb.early_stopping(150)])
    oof[va_i] = m.predict_proba(X.iloc[va_i])[:, 1]

# Soglia smussata — media dei top-1% candidati, NON solo l'argmax
ths = np.linspace(0.35, 0.65, 601)
accs = [((oof > t) == y).mean() for t in ths]
smooth_t = ths[np.argsort(accs)[-6:]].mean()   # ≈ 0,527

Perché "smussata"?

Se prendiamo solo la singola soglia che massimizza l'accuracy OOF, potremmo prendere un picco rumoroso che non generalizza. Mediare le top-1% delle soglie candidate dà un valore più robusto che tiene su dati nuovi.

STEP 14Lezioni apprese

  • Leggere il data dictionary come input avversariale. Ogni riga è un indizio.
  • Una singola feature sospettosamente forte è un'ipotesi di leak, non un risultato. Testala.
  • Controllare sempre train.isna() vs test.isna() — external_pd_score è stato beccato in una riga.
  • Validare contro il task reale, non contro fold random. Rolling next-month era la metrica che contava.
  • Non inseguire il public leaderboard. Il floor del rumore è più grande dei tuoi miglioramenti.
  • A volte il miglior feature engineering è la cancellazione. Abbiamo rimosso di proposito le 4 colonne più "predictive".
  • Quantificare le scelte etiche. "Abbiamo droppato race/religion" è debole. "Droppendole costa esattamente +0,7 pt di accuracy guidata da bias" è forte.
